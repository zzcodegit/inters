# Отчёт о проделанной работе

**Дата:** 17 марта 2025  
**Проект:** VPN Node — Stage 4 Dataplane (reliable streaming)  
**Задача:** Диагностика проблемы "Empty reply from server" при работе через Docker

---

## Контекст

После реализации Stage 4 (надёжная доставка через ReliableStream) сквозной маршрут **client → relay → exit → target** работал, но клиент не получал ответы. `curl` возвращал "Empty reply from server".

Наблюдалось:
- Exit получает запрос, отправляет HTTP-ответ и эмитит DATA-чанки
- Relay получает чанки (например, 215 байт) и пересылает их
- Клиент получает только маленькие ACK-пакеты (payload_len=28)
- Большие пакеты ответа (215+ байт) от relay к client не доходили

---

## Выполненные шаги

### 1. Исправления логики (до начала сессии)

- **Exit flush logic** (`src/roles/exit.rs`): флаш к target только при `end_of_stream` (пустой фрейм по порядку), а не при любом пустом фрейме
- **Client idle timeout** (`src/roles/client.rs`): HTTP/1.1-клиенты часто не делают half-close; добавлен таймаут неактивности 100 ms вместо ожидания EOF
- **ReliableStream out-of-order empty frames** (`src/stream_reliable.rs`): хранение out-of-order пустых фреймов в `recv_buffer` и доставка при появлении следующих data-фреймов по порядку
- **Relay address detection** (`src/roles/relay.rs`): использование `from != client_addr` вместо `from == exit_addr` для избежания IPv4/IPv6 несоответствий
- **Unit test** для out-of-order empty frame
- **Docker**: добавлены curl и сервис `test-curl` в compose

### 2. Диагностика потери пакетов

- Добавлено логирование:
  - `client udp recv large packet (likely response)` при приёме пакетов >100 байт
  - `relay forwarding large packet exit->client` при пересылке больших пакетов
- Подтверждено: exit отправляет, relay пересылает, client не логирует приём больших пакетов — потеря между relay и client

### 3. Изоляция: Native vs Docker

Создан скрипт `run-local.ps1` для запуска без Docker:
- target, exit, relay, client — отдельные процессы на localhost
- Динамические порты (40000–50000) для избежания конфликтов
- Логирование в `run-local-logs/`

**Результат native-запуска:** всё работает корректно:
- Relay получает пакеты от client и exit
- Exit отправляет response DATA (218 байт)
- Relay пересылает их клиенту
- Клиент получает: `client udp recv large packet len=218 from=127.0.0.1:44802`

### 4. Повышение уровня логирования

- В relay `debug!` заменён на `info!` для сообщения "relay received packet" — упрощение отладки
- Добавлен DEBUG-лог "relay forwarding exit->client" при пересылке

## Вывод

| Среда           | Результат                     |
|-----------------|-------------------------------|
| Native Windows  | ✅ Работает полностью         |
| Docker Desktop  | ❌ Большие UDP-пакеты теряются |

**Причина:** известные ограничения Docker Desktop / WSL2 под Windows по работе с UDP:
- [Docker UDP forwarding corruption (4.40+)](https://github.com/docker/for-win/issues/14823)
- [Fragmented UDP packets dropped in WSL2](https://github.com/microsoft/WSL/issues/6082)
- Общие проблемы с UDP в Docker Desktop на Windows

---

## Рекомендации

1. **Локальная разработка и тесты** — использовать native-запуск:
   ```powershell
   .\run-local.ps1
   ```

2. **Проверка в Docker** — использовать Linux-хост (VM, WSL2 без Docker, или удалённый сервер).

3. **Опционально:** уменьшение размера чанков ответа (например, <100 байт) может помочь при работе через Docker на Windows, но решение будет менее надёжным.
